# Security model

How SecureVault keeps documents private, what each key does, and what the
app deliberately does not promise. The decisions behind this are in the ADRs
under `docs/adr`; this page is the map.

## Threat model

SecureVault protects documents at rest on a phone that may be lost, stolen,
or handed to someone else for a moment. It assumes the operating system is
intact and the secure hardware works. It does not defend against a jailbroken
or rooted device with a debugger attached, a malicious OS update, or someone
who knows the app PIN and has the unlocked phone in hand. Nothing is sent
anywhere: there is no account, no analytics, and no network access.

## Key hierarchy

```
device key (hardware-backed, never leaves the secure hardware)
├── every vault entry: files, thumbnails, pages, small values
│     AES-256-GCM, 1 MiB chunks, chunk index as associated data (ADR 0002)
└── _database_key entry: 32 random bytes
      └── SQLCipher index: titles, tags, dates, fields, extracted text (ADR 0002)

app PIN ─── PBKDF2-SHA256 record in the secure store, never a key (ADR 0003)

backup passphrase ─── PBKDF2-HMAC-SHA256, 600 000 iterations, per-file salt
      └── backup key, held in memory for the length of one export or restore,
          never stored (ADR 0007)
```

### Device key

- iOS: an AES-256 key generated by the app and stored in the Keychain with
  `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` and a `userPresence` access
  control. Reading it prompts Face ID, Touch ID, or the device passcode; the
  key never syncs and is not in device backups.
- Android: an AES-256 key in the Android Keystore with user authentication
  required and a 300-second validity window, so the chunked cipher can run
  without a `CryptoObject` per call. Once the window lapses the module reports
  `KEY_LOCKED` and the app re-prompts and retries (ADR 0003). One prompt is
  open at a time: a caller that needs the key while a prompt is showing waits
  for that prompt's answer instead of opening a second one, which would take
  over the first one's callback and leave it waiting forever.
  "Delete everything" keeps the device key. On Android, if the system has
  invalidated it (`KEY_INVALIDATED`, after a biometric or lock screen change;
  iOS has no such state), the next setup replaces it with a new one, but only
  when the vault holds no entries, so nothing still encrypted under the old
  key is cut off by setup.

Everything the vault stores is encrypted under this key with AES-256-GCM.
Files are streamed in 1 MiB chunks, each with its own random nonce and the
chunk index as associated data, so a chunk cannot be dropped, reordered, or
moved between files without the tag failing.

### Database key

The searchable index is a SQLCipher database. Its key is 32 random bytes
generated once, stored as an ordinary vault entry (`_database_key`) under the
device key, and passed to `PRAGMA key` on every open. On disk the database
and its WAL have no readable header, strings, or schema.

A new key is written only when the vault's entry listing (which reads the
directory and needs no device key) succeeds without a `_database_key` entry,
and the SQLite folder holds no index file under any name a restore may have
given it (`securevault.db` or `securevault-<n>.db`; a leftover `-wal`, `-shm`
or `-journal` file without its database does not count). If `_database_key`
is listed but cannot be read (a locked or invalidated device key, any other
read failure, or a value that is not 64 hex characters), the open stops with
a typed error and the entry is left as it is. It also stops if either listing
fails, or if the key is missing while an index file exists. A replaced key
would make the existing index unreadable. "Delete everything" removes every
index file and its side files, so the next open after it starts as a first
run.

A restore moves the index in under a new name and then records it in
`_database_file`; if recording the name fails, the file is moved back and the
restore fails as a whole. A vault without that entry uses `securevault.db`.
If the entry is listed but cannot be read or holds no index name, the default
is used as a guess, and nothing is swept on it. Neither default is used while
a restored index file exists, and a named file that is missing while another
index file exists is a stale name: in both cases the open stops with a typed
error. Leftover files are swept only after opening a file that already
existed under a name that was not a guess. A failed listing of the vault's
entries or of the SQLite folder stops the open too. A locked device key while
reading the name or checking the prototype's JSON index stops the open with
`KEY_LOCKED`, which the key-recovery prompt and "Try again" handle. While "Delete everything" runs, an open is turned away with a
plain sentence instead of creating a file the erase would delete under it or
leave without its key. If the erase ends with `_database_key` or
`_database_file` still listed, it reports that it did not finish, and it can
be run again. The erase first closes the index and any connection a restore
replaced; if one of them does not close, it deletes nothing and reports that
it did not finish, and relaunching the app releases that connection.

### App PIN

The 6-digit PIN is the fallback door when biometrics are unavailable. It is
not an encryption key: the vault module keeps its own key, and the PIN only
gates the app's session. The PIN is stored as a PBKDF2-SHA256 hash with a
random salt in the platform secure store, together with the lockout state.

Every fifth consecutive wrong PIN pauses the keypad, starting at 30 seconds and
doubling up to an hour; a successful unlock, by PIN or by the device key,
resets the count. The lockout is read at launch, before the lock screen takes
a PIN, and again before every attempt, which is judged against the stricter of
the stored copy and the one in memory. Attempts are judged one at a time. A
relaunch therefore keeps a running pause and continues the count, and a failed
write cannot hand attempts back. A cancelled device-key prompt after a correct
PIN is not a wrong PIN and does not count.

A pause never runs longer than the one its count earned, measured from the
current clock: a stored pause beyond that, from a clock moved back or a corrupt
value, is capped and the cap is written back, so it ends on time instead of
sliding with the clock. If the stored lockout cannot be read, the app assumes a
30-second pause without inventing failures and does not overwrite the
unreadable copy; content that is not valid JSON is replaced with that pause.
Either way the pause ends on its own, so a broken store slows guessing down
without keeping the owner out.

### Backup key

A backup is the only way data leaves the vault. Its key is derived from a
passphrase the user types twice, with PBKDF2-HMAC-SHA256 at 600 000 iterations
and a fresh 16-byte salt written into the file header. The key exists only
while the module encrypts or decrypts the entries and is never written
anywhere. A wrong passphrase fails on a check entry before the vault is
touched, and every entry is decrypted once, to nothing, before the first
vault file is replaced, so a damaged backup is refused with the vault
intact. Every length the file declares is checked against the bytes left in
it before a buffer is allocated, a backup without its document index is
refused before the key is derived, and on Android the device key is used
once more right before the vault is cleared, so a lapsed authentication
window is reported with nothing removed. Writing the entries back is not a
transaction: a disk or key failure at that point is reported as a partial
restore, and the user restores again. A failed encryption or decryption
removes its own half-written file.

## Session

The root layout mounts document routes only while the session is unlocked,
so no deep link or navigation call can reach them while locked. Auto-lock
runs on a timer after the app leaves the foreground, with system pickers and
share sheets excluded so the vault does not lock behind them. The privacy
screen blurs the app in the switcher and blocks screenshots and recording
while unlocked. Sharing can require a second biometric check.

A share sheet is system UI and would open over the lock screen, so the app
opens one only for the unlocked session that asked for it. A backup export or
a document share that is still being prepared when the vault locks, or when
its screen goes away, is deleted without being shared. If the app left the
foreground meanwhile, the share waits until it is back and auto-lock has
judged the time away. The outcome of such an export or share is shown as one
plain sentence after the next unlock, with no file name, size, or entry count;
toasts are cleared when the vault locks. A restore is not stopped by the lock,
so the vault is never left half replaced; it finishes and reports after the
next unlock. Only one export, restore, or erase runs at a time: the backup
service refuses a second one while the first is still running, also when the
first was started before the last lock, and Settings keeps those actions
disabled until it ends.

## What touches the disk unencrypted

- Decrypted previews, rendered PDF pages, share copies, and undo copies live
  in the app's cache directory while a screen needs them. The cache is swept
  when the vault locks, when the app is deleted, and on the share sheet's and
  the undo window's own timers.
- While a backup is written, the vault module decrypts one entry at a time
  into a staging folder in the cache and removes it as soon as that entry is
  encrypted under the backup key. The folder is emptied before and after every
  export and by the lock and launch sweep, so an export killed mid-entry leaves
  at most one entry behind, and only until the next launch or lock. The module
  sweeps only that exact folder: the path it is given must resolve, links and
  `..` included, to the cache's own `backup-staging`, or the export is refused
  before anything is touched. If the folder cannot be listed or emptied, the
  export fails on both platforms, also after the container was written, and
  the finished file is removed, so no success is reported next to leftover
  plaintext.
- A restore decrypts the same way, into the cache's own `restore-staging`
  folder under the same path check, and nothing it reads or decrypts goes to
  the system temporary folder. Each entry's plaintext is removed once it is
  re-encrypted under the device key, and the folder is emptied before and
  after every restore. A restore killed mid-entry leaves at most a payload
  copy and one decrypted entry there, until the next launch: the launch sweep
  removes the folder, and so does any lock with no restore running. A lock
  during a restore leaves it alone, because the restore goes on and empties
  it when it ends.
- Thumbnails are encrypted from memory on Android. On iOS the downsampled
  JPEG passes through one `thumb_` file in the cache, which the lock and
  launch sweep removes if the app is killed before the module does.
- Backup ciphertext is not left behind either. A finished container is
  removed once the share sheet closes, and the document picker's copy of a
  backup chosen for restore is removed after the restore or when its sheet
  closes. The lock and launch sweep removes both cache folders, `backup` and
  `DocumentPicker`, except while a restore is still reading them. An export
  that is running when the vault locks is not cancelled natively: the lock
  also empties the cache's `backup-staging` folder, so it fails at its next
  entry, at most the entry being written was staged after the lock, and a
  container it still finishes is deleted unshared.
- Importing a PDF or image from Files goes through the document picker,
  which writes a plaintext copy of the file into the same `DocumentPicker`
  cache folder under a random name. On iOS the system hands the app its own
  copy first, in `tmp/com.naderalfakesh.securevault-Inbox`; the add screen
  removes that one, by its exact name, as soon as the picker has made its
  copy. Photos chosen from the library or taken with the camera are copied
  into the cache's `ImagePicker` folder. Scanned pages are written to `tmp`
  as `scan_<batch>_<page>.jpg` on iOS and copied by the ML Kit client into
  the cache's `mlkit_docscan_ui_client` folder on Android. A PDF's preview is
  rendered into a `pages_preview_` cache folder.
- The add screen removes these copies as soon as the document is saved, and
  whenever it lets go of them unsaved: back to the sources, closing the
  screen, the vault locking, or a picker or scanner that answers after the
  screen has gone. A save that is already running when the screen goes keeps
  its copies until the vault module has read them, then removes them either
  way, and reports its outcome after the next unlock if the vault locked. A
  save that fails on screen keeps the copies only so it can be retried.
- The lock and launch sweep removes the `ImagePicker`, `mlkit_docscan_ui_client`
  and preview folders, the iOS Inbox folder and scanner pages, and the
  `DocumentPicker` folder (outside a restore, as above), so a copy left by a
  crash or a kill goes at the next launch. Every removal is guarded: only an
  entry directly inside one of those exact folders, or an iOS `tmp` file with
  exactly the scanner's name pattern, after decoding and with `..` refused,
  is ever removed; the user's own files elsewhere are never touched.
- Launch also removes, once, plaintext scratch that earlier builds wrote and
  could leave when killed: `tmp/backup-<UUID>` and `tmp/<UUID>` on iOS,
  `backup<n>.tmp` in the cache and `vault<n>.tmp` in the vault folder on
  Android. Only plain files with exactly those names, directly in those
  folders, are removed.
- Still open: a lock while a save is running can sweep a picked copy before
  the vault module has opened it, so that save fails (and says so after the
  next unlock) rather than leaving the copy. Google Play services keeps its
  own copy of scanned pages until the ML Kit client asks it to clean up; that
  copy is outside the app's storage. These removals are checked by tests;
  the native QA pass on a simulator and an emulator is still owed.
- OCR text is stored only inside the encrypted index.
- Screenshots are blocked while unlocked; on the iOS simulator the frame
  buffer can still be captured, which is a simulator property.

## Honest limits

- Biometric prompts and the Keystore window are the platform's; the app
  cannot verify a real fingerprint or face, only the system's answer.
- A device backup (iCloud, Google) does not include the device key, so the
  vault does not restore from it. That is intended: the passphrase backup is
  the supported path.
- The heuristic that suggests titles and dates runs on extracted text on the
  device; nothing is uploaded to a model.
