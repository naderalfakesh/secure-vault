# Security model

How SecureVault keeps documents private, what each key does, and what the
app deliberately does not promise. The decisions behind this are in the ADRs
under `docs/adr`; this page is the map.

## Threat model

SecureVault protects documents at rest on a phone that may be lost, stolen,
or handed to someone else for a moment. It assumes the operating system is
intact and its Keychain and Keystore work as documented. It does not defend against a jailbroken
or rooted device with a debugger attached, a malicious OS update, or someone
who knows the app PIN and has the unlocked phone in hand. There is no
account, and SecureVault itself sends nothing anywhere and collects no
analytics. Google ML Kit, which reads document text on the device (and, on
Android, the Google Play services document scanner), sends Google usage and
performance metrics; see "Google ML Kit metrics" below.

## Key hierarchy

```
device key (iOS: Keychain item read into app memory; Android: non-exportable Keystore key)
├── every vault entry: files, thumbnails, pages, small values
│     AES-256-GCM, 1 MiB chunks, chunk index as associated data (ADR 0002)
└── _database_key entry: 32 random bytes
      └── SQLCipher index: titles, tags, dates, fields, extracted text (ADR 0002)

app PIN ─── PBKDF2-SHA256 record in the secure store, never a key (ADR 0003)

backup passphrase ─── PBKDF2-HMAC-SHA256, 600 000 iterations, per-file salt
      └── backup key, held in memory for the length of one export or restore,
          never stored (ADR 0007)
```

### Device key

- iOS: 32 random bytes generated by the app with `SecRandomCopyBytes` and
  stored as a Keychain item with `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`
  and a `userPresence` access control. Reading it prompts Face ID, Touch ID,
  or the device passcode; the key never syncs and is not in device backups.
  It is a Keychain-protected key, not a Secure Enclave key: every vault
  operation reads the raw bytes into process memory as a CryptoKit
  `SymmetricKey` for as long as that operation runs.
- Android: an AES-256 key generated inside the Android Keystore with user
  authentication required and a 300-second validity window, so the chunked
  cipher can run without a `CryptoObject` per call. The key material is not
  exportable; the app holds a reference and the Keystore performs each
  AES-GCM call. Whether that runs in secure hardware depends on the device.
  Once the window lapses the module reports `KEY_LOCKED` and the app
  re-prompts and retries (ADR 0003). When that prompt is cancelled or cannot
  be shown, the screen says in a plain sentence that the device key was not
  unlocked, never the Keystore's own "User not authenticated". One prompt is open at a time: a caller
  that needs the key while a prompt is showing waits for that prompt's answer
  instead of opening a second one, which would take over the first one's
  callback and leave it waiting forever.
  "Delete everything" keeps the device key. On Android, if the system has
  invalidated it (`KEY_INVALIDATED`, after a biometric or lock screen change;
  iOS has no such state), the next setup replaces it with a new one, but only
  when the vault holds no entries, so nothing still encrypted under the old
  key is cut off by setup. With entries left, setup stops and says in a plain
  sentence that the screen lock or biometrics changed and those documents
  cannot be opened on this device.

Everything the vault stores is encrypted under this key with AES-256-GCM.
Files are streamed in 1 MiB chunks, each with its own random nonce and the
chunk index as associated data. A chunk that was altered, or moved to a
different position, fails its tag. The index is the only associated data, so
the v1 container does not detect two things: a file cut short at a chunk
boundary reads as complete, and a chunk at the same index in another file
under the same key would also decrypt. Nothing else binds a chunk to its
file or records the expected chunk count.

### Database key

The searchable index is a SQLCipher database. Its key is 32 random bytes
generated once, stored as an ordinary vault entry (`_database_key`) under the
device key, and passed to `PRAGMA key` on every open. On disk the database
and its WAL have no readable header, strings, or schema.

A new key is written only when the vault's entry listing (which reads the
directory and needs no device key) succeeds without a `_database_key` entry,
and the SQLite folder holds no index file under any name a restore may have
given it (`securevault.db` or `securevault-<n>.db`; a leftover `-wal`, `-shm`
or `-journal` file without its database does not count). If `_database_key`
is listed but cannot be read (a locked or invalidated device key, any other
read failure, or a value that is not 64 hex characters), the open stops with
a typed error and the entry is left as it is. It also stops if either listing
fails, or if the key is missing while an index file exists. A replaced key
would make the existing index unreadable. "Delete everything" removes every
index file and its side files, so the next open after it starts as a first
run. That open waits for setup: after a successful erase every open is
turned away with `VAULT_EMPTIED`, before it reads or writes any vault entry,
so a screen that refreshes its list on the erase's change notice neither
creates `_database_key` and an empty `securevault.db` nor triggers a device
key prompt. The lists show no documents meanwhile. A successful setup lifts
this before the app unlocks, and the first screen behind the lock then
creates the key and the index. The hold lives in memory; after a relaunch
the cleared PIN record sends the app to setup anyway. A refused delete of
the PIN record is tried once more; if it fails again, the erase is still
reported, with a sentence that the old PIN could not be removed and the
vault should be set up again now. Until setup replaces it, the old PIN still
unlocks after a relaunch, and the empty vault then behaves as a first run:
the first screen creates a new key and index without setup.

A restore moves the index in under a new name and then records it in
`_database_file`. If recording the name fails, the file is moved back out of
the SQLite folder, but the vault's entries have already been replaced, so the
restore ends as a partial one with `BACKUP_INDEX`: the documents are back,
the index is not, and the user restores again. A vault without that entry uses `securevault.db`.
If the entry is listed but cannot be read or holds no index name, the default
is used as a guess, and nothing is swept on it. Neither default is used while
a restored index file exists, and a named file that is missing while another
index file exists is a stale name: in both cases the open stops with a typed
error. Leftover files are swept only after opening a file that already
existed under a name that was not a guess. A failed listing of the vault's
entries or of the SQLite folder stops the open too. A locked device key while
reading the name or checking the prototype's JSON index stops the open with
`KEY_LOCKED`, which the key-recovery prompt and "Try again" handle. While "Delete everything" runs, an open is turned away with a
plain sentence instead of creating a file the erase would delete under it or
leave without its key. If the erase ends with `_database_key` or
`_database_file` still listed, it reports that it did not finish, and it can
be run again. The erase first closes the index and any connection a restore
replaced; if one of them does not close, it deletes nothing and reports that
it did not finish, and relaunching the app releases that connection. An
erase that did not finish still runs the cache sweep, which touches only the
decrypted copies and the image caches.

### App PIN

The 6-digit PIN is the fallback door when biometrics are unavailable. It is
not an encryption key: the vault module keeps its own key, and the PIN only
gates the app's session. The PIN is stored as a PBKDF2-SHA256 hash with a
random salt in the platform secure store, together with the lockout state.

Every fifth consecutive wrong PIN pauses the keypad, starting at 30 seconds and
doubling up to an hour; a successful unlock, by PIN or by the device key,
resets the count. The lockout is read at launch, before the lock screen takes
a PIN, and again before every attempt, which is judged against the stricter of
the stored copy and the one in memory. Attempts are judged one at a time. A
relaunch therefore keeps a running pause and continues the count, and a failed
write cannot hand attempts back. A cancelled device-key prompt after a correct
PIN is not a wrong PIN and does not count. Change PIN judges the current
PIN the same way: against the same lockout, one attempt at a time, and a
wrong one counts, so an unlocked session cannot guess the PIN without limit.
While the pause runs, Change PIN does not check the PIN at all. The device
unlock on the lock screen still opens the vault and ends the pause, so a
lockout slows guessing down without keeping the owner out.

A pause never runs longer than the one its count earned, measured from the
current clock: a stored pause beyond that, from a clock moved back or a corrupt
value, is capped and the cap is written back, so it ends on time instead of
sliding with the clock. If the stored lockout cannot be read, the app assumes a
30-second pause without inventing failures and does not overwrite the
unreadable copy; content that is not valid JSON is replaced with that pause.
Either way the pause ends on its own, so a broken store slows guessing down
without keeping the owner out.

A missing record is not taken at its word. On Android, expo-secure-store
deletes an entry it can no longer decrypt ("out of sync with the keystore")
and returns nothing, so a damaged PIN record would read as no PIN, and a
damaged lockout as no failures. Each record therefore has a plain marker
file, `securevault-session/pin` and `securevault-session/lockout` in the
documents folder next to the vault's entries. The markers hold nothing
secret, are not vault entry names (so listings, backups and restores never
see them), are written right after their record, and are written again
whenever the record is read, which also marks records from builds before
markers. A lockout record that is gone while its marker exists is the
30-second fail-safe pause above, written back, never a reset. A PIN record
that is gone while its marker exists reads as unreadable, and with the
device key present the session is `unavailable`, not setup (see Session).
Without a device key the marker guards nothing, for example after a device
backup brought the documents folder back without the Keychain or Keystore,
and setup runs as before. "Delete everything" removes the markers before
the records; if a marker cannot be removed, no record is deleted and the
erase reports that the old PIN could not be removed. iOS's Keychain does not
drop entries like this, but the same rule applies there. The marker folder
is excluded from iCloud and iTunes backups (`isExcludedFromBackup`), and
Android's backup rules include only shared preferences, so the files folder
never leaves the device. A restored phone therefore has no markers: a PIN
record that came back with it reads as present and is marked again, and one
that did not is a first run, exactly as before markers existed.

### Backup key

A backup is the only way the whole vault leaves the device. Its key is
derived from a passphrase the user types twice, with PBKDF2-HMAC-SHA256 at
600 000 iterations and a fresh 16-byte salt written into the file header. The
key exists only while the module encrypts or decrypts the entries and is never
written anywhere. A wrong passphrase fails on a check entry before the vault is
touched, and every entry is decrypted once, to nothing, before the first
vault file is replaced, so a damaged backup is refused with the vault
intact. Every length the file declares is checked against the bytes left in
it before a buffer is allocated, and on Android the device key is used
once more right before the vault is cleared, so a lapsed authentication
window is reported with nothing removed.

Before the key is derived, a restore also refuses anything a version-1
exporter never wrote. The header's KDF name, cipher and iteration count must
be the ones every committed exporter has written (`pbkdf2-hmac-sha256`,
`aes-256-gcm`, exactly 600 000), so a crafted header cannot make PBKDF2 run
for hours; other settings end in `BACKUP_UNSUPPORTED`. The version must be 1
(a higher one is `BACKUP_UNSUPPORTED`), every header field must be present
with its JSON type, and the header must count at least three entries. The
entries must have the exported shape: the check entry first and only there,
no kind other than `c`, `s`, `f` and `x`, no key twice, exactly one `database`
extra and a `_database_key` string, and nothing after the last entry. Any
other shape is `BACKUP_INVALID`. A later exporter that changes any of this
must bump the version. Both platforms apply the same rules in the same order.

Memory and disk are checked before the vault is cleared as well, with no
fixed size limit. On iOS each header and entry name is compared with the
memory the OS says the process can still use before it is read. On Android
the allocation itself is the check: a refused allocation is a typed
`BACKUP_RESOURCE`, never an untyped crash. After every entry has decrypted
once, the largest string entry must fit three times on iOS (the OS figure)
and four times on Android (a trial allocation the VM may collect for), and
the restored vault, a second copy of the index for its move and first open,
and one entry's temporary files must fit in the free space plus what the old
vault's entries give back. The first restored entry's temporary files (its
payload copy and its plaintext, at most twice its payload) are written before
the old vault goes, so they must fit in the free space alone. Free space is
the figure the OS gives for space the app can really write: iOS's capacity
for important usage, and on Android 8 and later the usable space capped by
StorageManager's allocatable bytes minus SecureVault's own cache. The
allocatable figure leaves out the system's low-storage reserve, so a restore
that would push the device into it is refused; it counts caches the system
could clear, but the app's own cache holds the staging folders the restore
reads, so it is never counted as room, and nothing is cleared to make room.
The picked backup is not in the cache by then (see below): it sits in the
app's files, where it already counts as used space and is never counted as
room on either platform. If the figure cannot be read, the usable space alone is
used, as it is before Android 8. Otherwise the restore stops with
`BACKUP_RESOURCE` or `BACKUP_NO_SPACE` and nothing changed. Neither check is
a guarantee: memory can be taken or the disk can fill during the restore,
and iOS ends a process that runs out of memory instead of reporting it.

Writing the entries back is not a transaction: a disk or key failure at that
point is reported as a partial restore, and the user restores again. An index
that decrypts but cannot be opened is only found after the vault was
replaced, and is reported as `BACKUP_INDEX`. A failed encryption or
decryption removes its own half-written file.

Only the entry payloads are authenticated. The container header (format
version, KDF parameters, entry count) and each entry's name and kind are plain
JSON outside the AEAD, so the tag does not detect an edited header or entry
name, and the entry count in the header is what the reader trusts.

## Session

The root layout mounts document routes only while the session is unlocked,
so no deep link or navigation call can reach them while locked.

Launch reads the device key's presence and the PIN record as three states:
present, absent, or unreadable. A key and a PIN open the lock screen; no
PIN sends the app to setup, which keeps any key it finds. If either read
fails, the session is `unavailable`: a screen of its own that offers
"Try again" (and tries again on each return to the foreground), writes
nothing, and never falls back to setup, which would create a new key over a
vault it could not see. When the cause is a PIN record that its marker says
was written (see App PIN) and the device key is there, the screen also
offers "Set a new PIN": it asks for the device key's own gate (biometrics or
the device passcode, the same door the lock screen's device-unlock button
opens) and only then goes to setup, which keeps the key and the documents
and adds a new PIN. Nobody who cannot already open the vault with the
device key can replace the PIN this way, and a relaunch forgets that the
gate was opened. On Android the key behind that gate may have been invalidated
(the screen lock or biometrics changed). Then the documents in the vault can
never be decrypted on this device again: with entries left, the screen says so
in a plain sentence and offers only "Delete everything", behind the same
native confirmation as in Settings, after which setup replaces the key. A
vault with no entries goes straight on to setup, which replaces the key as it
always has. Setup reads both again right before it creates a
key: an unreadable one ends in `unavailable`, and a key with a PIN and
entries ends on the lock screen with the PIN untouched. An unreadable PIN
record while unlocking is not a wrong PIN and does not count towards the
lockout. On iOS the key check reports a key whenever the Keychain says
anything but "not found", so there `unavailable` comes from the PIN record
read (for example before the phone's first unlock).

The "Face ID" (biometric unlock) setting decides only whether the lock screen
opens the biometric prompt by itself and shows the biometric key. Turned
off, the lock screen asks for the PIN first; the device-unlock button stays,
and the device key keeps its own OS gate, so iOS can still ask for Face ID or
the passcode when the PIN path reads the key.

Onboarding's last step (enable biometrics) runs after setup has saved the
PIN and unlocked the device key, but before the session is `unlocked`.
Auto-lock does not time that step, and the privacy cover is not shown
there: it is only offered for a new or emptied vault, so the vault holds no
documents at that point. A kill or relaunch during the step opens the lock
screen, because the key and the PIN record already exist. Auto-lock
runs on a timer after the app leaves the foreground. System pickers and share
sheets pause it for a bounded time (2 minutes for a share sheet, 10 for other
system UI); a trip longer than that is judged against auto-lock as usual, and
a pause ends with the session that took it. The bound is checked whenever the
pause ends, not only on the return: Android delivers a chooser's Back or pick,
and a picker's result, just before the app is active again, so a pause that
ends while the app is still away and has outlived its bound excuses nothing.
The whole trip since the app left under it is judged against auto-lock right
then and again on the return. Only a pause that ends within its bound excuses
the time it covered. The privacy
screen blurs the app in the switcher and blocks screenshots and recording
while unlocked. Sharing can require a second biometric check.

A share sheet is system UI and would open over the lock screen, so the app
opens one only for the unlocked session that asked for it. A backup export or
a document share that is still being prepared when the vault locks, or when
its screen goes away, is deleted without being shared. If the app left the
foreground meanwhile, the share waits until it is back and auto-lock has
judged the time away.

When the vault locks while a share sheet is open, the share ends with it. On
iOS the lock dismisses the share sheet, together with anything it presented,
and deletes the copy. Android's chooser is an activity of its own, which the
app cannot close, and while it is up the app is paused and its JavaScript
timers stop. So before the chooser opens, a native main-looper timer is armed
to delete the copy's folder once the time away could have locked the vault (the
longer of 2 minutes and the auto-lock setting; none with auto-lock off). A
target picked after that from a chooser still on screen opens a content URI
whose file is gone and receives nothing; the vault itself locks on return. A
target picked before that, on either platform, has the file, and SecureVault
cannot control what that app keeps. After the unlock the document's viewer
says the share was interrupted and the copy removed. The outcome of an export or
an interrupted preparation is shown as one
plain sentence after the next unlock, with no file name, size, or entry count;
toasts are cleared when the vault locks. A restore is not stopped by the lock,
so the vault is never left half replaced; it finishes and reports after the
next unlock. Only one export, restore, or erase runs at a time: the backup
service refuses a second one while the first is still running, also when the
first was started before the last lock, and Settings keeps those actions
disabled until it ends.

## What touches the disk unencrypted

- Decrypted previews, rendered PDF pages, share copies, and undo copies live
  in the app's cache directory while a screen needs them. The cache is swept
  when the vault locks, when the app is deleted, and on the share sheet's and
  the undo window's own timers.
- Decrypted images are shown through one image component that keeps them in
  the image library's memory cache only, never its disk cache; a lint rule
  refuses the library's own image component anywhere else in the app. The
  lock and launch sweep clears the image library's memory and disk caches as
  well, so copies an older build left in the iOS disk cache are removed too.
- While a backup is written, the vault module decrypts one entry at a time
  into a staging folder in the cache and removes it as soon as that entry is
  encrypted under the backup key. The folder is emptied before and after every
  export and by the lock and launch sweep, so an export killed mid-entry leaves
  at most one entry behind, and only until the next launch or lock. The module
  sweeps only that exact folder: the path it is given must resolve, links and
  `..` included, to the cache's own `backup-staging`, or the export is refused
  before anything is touched. If the folder cannot be listed or emptied, the
  export fails on both platforms, also after the container was written, and
  the finished file is removed, so no success is reported next to leftover
  plaintext.
- A restore decrypts the same way, into the cache's own `restore-staging`
  folder under the same path check, and nothing it reads or decrypts goes to
  the system temporary folder. Each entry's plaintext is removed once it is
  re-encrypted under the device key, and the folder is emptied before and
  after every restore. A restore killed mid-entry leaves at most a payload
  copy and one decrypted entry there, until the next launch: the launch sweep
  removes the folder, and so does any lock with no restore running. A lock
  during a restore leaves it alone, because the restore goes on and empties
  it when it ends.
- Thumbnails are encrypted from memory on Android. On iOS the downsampled
  JPEG passes through one `thumb_` file in the cache, which the lock and
  launch sweep removes if the app is killed before the module does.
- Backup ciphertext is not left behind either. A finished container is
  removed once the share sheet closes. The document picker copies a backup
  chosen for restore into the cache's `DocumentPicker` folder, which the
  system may purge under low storage (Android's storage service did, with
  the restore sheet open). Before the app reads the header, that copy is
  moved (a rename on the same volume, no extra space) into the documents
  folder's `restore-source` folder (Android `files`, iOS `Documents`), which
  is not purged, under a fixed name; nothing stays in the cache. A failed
  move removes both the cache copy and the folder and ends with
  `BACKUP_RESTORE_STAGING_INVALID`. The kept copy is removed after the
  restore or when its sheet closes. The lock and launch sweep removes the
  `backup`, `DocumentPicker` and `restore-source` folders, except while a
  restore is still reading them, and a second pick is refused then. The
  vault module removes `restore-source` as a whole, the same no-follow way
  as the cache folders, and never an entry below it or beside it in the
  documents folder. On iOS the folder is excluded from device backups
  when it is created; on Android the backup rules leave the files folder
  out. An export
  that is running when the vault locks is not cancelled natively: the lock
  also empties the cache's `backup-staging` folder, so it fails at its next
  entry, at most the entry being written was staged after the lock, and a
  container it still finishes is deleted unshared.
- Importing a PDF or image from Files goes through the document picker,
  which writes a plaintext copy of the file into the same `DocumentPicker`
  cache folder under a random name. On iOS the system hands the app its own
  copy first, in `tmp/com.naderalfakesh.securevault-Inbox`; the add screen
  removes that one, by its exact name or the name the system gives a
  duplicate (a space or hyphen and a number before the extension), as soon
  as the picker has made its copy. Photos chosen from the library or taken with the camera are copied
  into the cache's `ImagePicker` folder. Scanned pages are written to `tmp`
  as `scan_<batch>_<page>.jpg` on iOS and copied by the ML Kit client into
  the cache's `mlkit_docscan_ui_client` folder on Android. A PDF's preview is
  rendered into a `pages_preview_` cache folder. A source that arrives as an
  Android `content://` URI is copied to `temp_import_<time>` in the cache so
  the vault module can read a path; that copy is removed as soon as the
  module has read it or the preview is rendered, whether that worked or not,
  so it never outlives the call that made it.
- The add screen removes these copies as soon as the document is saved, and
  whenever it lets go of them unsaved: back to the sources, closing the
  screen, the vault locking, or a picker or scanner that answers after the
  screen has gone. A save that is already running when the screen goes keeps
  its copies until the vault module has read them, then removes them either
  way, and reports its outcome after the next unlock if the vault locked,
  also when it settles after the lock but before the screen has gone. A
  save that fails on screen keeps the copies only so it can be retried.
- The lock and launch sweep removes the `ImagePicker`, `mlkit_docscan_ui_client`
  and preview folders, the iOS Inbox folder and scanner pages, any
  `temp_import_<digits>` copy, and the `DocumentPicker` folder (outside a
  restore, as above), so a copy left by a crash or a kill goes at the next
  launch. Every removal is guarded: only an entry directly inside one of
  those exact folders, a cache entry named exactly `temp_import_<digits>`, or
  an iOS `tmp` file with exactly the scanner's name pattern, after decoding
  and with `..` refused, is ever removed; the user's own files elsewhere are
  never touched.
- Every whole-folder removal in these sweeps (the two staging folders,
  `backup` and its restore extras, `DocumentPicker`, `ImagePicker`,
  `mlkit_docscan_ui_client`, the preview, viewer and share folders, and the
  iOS Inbox) goes through the vault module, which never follows a symbolic
  link: a link planted in place of one of these folders, or anywhere inside
  one, is removed itself and what it points at is left alone. The module
  only removes entries inside the app's cache (and, on iOS, its `tmp`) once
  the parent's links are resolved. expo-file-system's own `delete` is not
  used for these because on Android it empties a link's target before
  removing the link. An export starts by removing the cache's `backup`
  folder the same way and creating it anew, so a link planted there is
  unlinked before the index copy or the container is written; if it cannot
  be removed, the export stops with `BACKUP_STAGING_INVALID` before writing
  anything. A restore whose extras or staging folder cannot be cleared this
  way, for instance under a `backup` link that resolves outside the cache,
  stops with `BACKUP_RESTORE_STAGING_INVALID` before anything is read or
  replaced, and says so in a plain sentence.
- Launch also removes, once, plaintext scratch that earlier builds wrote and
  could leave when killed: `tmp/backup-<UUID>` and `tmp/<UUID>` on iOS,
  `backup<n>.tmp` in the cache and `vault<n>.tmp` in the vault folder on
  Android. Only plain files with exactly those names, directly in those
  folders, are removed.
- Still open: a lock while a save is running can sweep a picked copy before
  the vault module has opened it, so that save fails (and says so after the
  next unlock) rather than leaving the copy. Google Play services keeps its
  own copy of scanned pages until the ML Kit client asks it to clean up; that
  copy is outside the app's storage. These removals are checked by tests;
  the native QA pass on a simulator and an emulator is still owed.
- OCR text is stored only inside the encrypted index.
- "Copy text" in the viewer puts a document's extracted text on the system
  clipboard, which other apps can read. On iOS it is copied local-only (not
  offered to other devices through Universal Clipboard) and expires after 2
  minutes; on Android it is marked sensitive, so the clipboard preview and
  keyboards do not show it, and it has no expiry. When the vault locks, the
  clipboard is emptied if it still holds that text; anything copied since is
  left alone. A copy that is still there after the app was killed stays
  until iOS expires it or something else is copied.
- Screenshots are blocked while unlocked; on the iOS simulator the frame
  buffer can still be captured, which is a simulator property.

## Google ML Kit metrics

SecureVault uses Google ML Kit to read document text on the device, on both
platforms. On Android it also uses the Google Play services document
scanner, which runs inside Google Play services, outside the app. The app
keeps both, and discloses them on the protection page and the processing
sheet.

What is sent:

- ML Kit sends Google usage and performance metrics. Google's ML Kit data
  disclosure pages list: device information (manufacturer, model, OS version
  and build, ML hardware accelerators), app information (bundle ID or
  package name and app version), a per-installation identifier, performance
  metrics such as latency, API configuration such as image format and
  resolution, input and output size, feature version, event types and error
  codes. They are encrypted in transit.
- The `MLKitCommon` privacy manifest (pod 13.0.0) declares these collected
  data types, for analytics (and, except diagnostics, app functionality),
  not linked to the user and not used for tracking: device ID, performance
  data, product interaction, other diagnostic data, other user content, and
  other data types.
- ML Kit does not send your images or the text it reads: Google's ML Kit
  terms say processing happens on the device and that input data and
  results are not sent to Google servers. The manifest's "other user
  content" entry is Google's own declaration and is not explained further.
- The per-installation identifier means the metrics are not anonymous, even
  though Google says the identifier is not meant to identify a user or a
  device.

How it is sent: on iOS, `MLKitCommon` carries its own Clearcut uploader,
which queues events in `Library/Caches/CCTClearcutLogger` and reads Phenotype
configuration (the milestone 1 QA found both in the app container). On
Android the bundled text recognition logs through Google's data transport,
and the scanner logs from Google Play services.

This cannot be turned off. Neither ML Kit nor the scanner offers a setting,
Info.plist key or manifest flag for it. The `firebase_*` and
`FirebaseDataCollectionDefaultEnabled` switches belong to Firebase, which
SecureVault does not use, and the bundled and unbundled models log alike.

## Honest limits

- Biometric prompts and the Keystore window are the platform's; the app
  cannot verify a real fingerprint or face, only the system's answer.
- On iOS the vault key is a Keychain item, and the code that encrypts holds
  the raw key in memory while it runs. iOS data protection guards the
  Keychain itself; no dedicated key hardware generates or holds this key.
- A device backup (iCloud, Google) does not include the device key, so the
  vault does not restore from it. That is intended: the passphrase backup is
  the supported path.
- The heuristic that suggests titles and dates runs on extracted text on the
  device; nothing is uploaded to a model.
